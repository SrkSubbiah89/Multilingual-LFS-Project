Starting from flat retrieval (the better baseline), two independent
improvements were tested on the identical 18,747-case set.

\textbf{40.95\% is this thesis's headline, best-tested ISCO-08 result} ---

85.3\% an earlier internal draft stated. The two improvements are genuinely
additive (not redundant), consistent with them working through independent
mechanisms: embedding-model capacity (e5-large) versus input-text richness
(enrichment).

The enrichment improvement traces to a real, root-caused engineering defect:
every catalogue entry's embedding text was originally just
\texttt{"\{code\} \{2-4 word title\}"}, while the official ILO source
workbook already available to this project carries full definitions and
example occupation lists for every entry, discarded by the original
normalisation script. Several thin-text codes acted as a ``magnet,''
matching 15--55$\times$ more often than their true frequency. After
enrichment, these magnet codes' prediction counts returned close to their
true frequency (e.g.\ code 6122: 468$\to$24 predictions; code 5165:
276$\to$31).

\subsection{Does LLM Re-Ranking Help?}

\textbf{Six independent checks, run at different times, on different
configurations and providers, produced the same answer: no, with one
narrow exception.}

\begin{enumerate}
\item e5-large, no rerank vs.\ Groq rerank (500-case sample): 29.20\% both
  ways, byte-identical, 499/500 predictions unchanged.
\item Enrichment, reranked (642-case validation split): 32.55\%$\to$32.87\%,
  $+0.31$pp, not significant ($p=0.5$).
\item Production default (e5-small) on the previously-unused validation
  split (642 cases): 18.22\%$\to$18.69\%, $+0.47$pp, not significant
  ($p=0.25$) --- and all 4 differing predictions traced to the identical,
  single, already-known Armed Forces catalogue quirk (a 4-digit-code
  convention mismatch), not a general reranking effect.
\item Corrective-retry reformulation (a different mechanism from
  reranking, local model, $n=60$): 51.67\% both ways, exactly identical,
  McNemar $p=1$.
\end{enumerate}

Read plainly: retrieval quality, not generation/reranking quality, is the
real accuracy ceiling for this task. This finding held up across six
independent tests, different LLM providers, and two genuinely different
mechanisms (candidate reranking and query reformulation) --- a robust
result, reported as such.

\subsection{Does Retrieval Grounding Matter More Than Raw LLM Knowledge?
Zero-Shot Classification and a Query-Translation Fix}
\label{sec:results-translation}

A natural follow-on question, prompted directly during a late-stage review
of this work (2026-09-10): if a large cloud model does not help as a
\emph{reranker} on top of retrieval, could it replace retrieval entirely?
Groq's \texttt{gpt-oss-120b} was asked to classify job descriptions
directly to a 4-digit ISCO-08 code with \emph{no} candidate list and no
retrieval step at all --- genuinely untested territory in this project,
distinct from every reranking check above.

\textbf{Result: 18.83\% ($n=324$) --- below the 21.19\% flat-retrieval
baseline.} Read plainly: an LLM's general knowledge alone, without being
handed the actual catalogue to search over, is \emph{worse} than simple
retrieval. This is informative in itself: it demonstrates that the
engineered retrieval architecture this thesis builds is doing real,
necessary work, not something a sufficiently large model would render
unnecessary.

Investigating \emph{why} retrieval-grounded classification underperforms
for non-English queries specifically led to a second, genuinely positive
finding. The enriched catalogue's embedding text (Section~\ref{sec:res-isco})
is English-sourced --- official ILO definitions and example
job titles. A non-English query therefore embeds further from its true
catalogue match than an English translation of the same query would,
even though the embedding model itself is multilingual. Translating
non-English \texttt{job\_title} text to English via a local model
(\texttt{qwen2.5:3b}, no API cost) immediately before embedding, with no
other change to the retrieval pipeline, was tested on a 60-case
stratified dev-split sample (15 cases each of Arabic, Hindi, Urdu,
Tagalog):

\begin{table}[h]
\centering
\begin{tabular}{lrr}
\toprule
Language & Original-language query & Translated to English first \\
\midrule
Arabic & 40.0\% & 60.0\% \\
Hindi & 40.0\% & 66.7\% \\
Urdu & 26.7\% & 33.3\% \\
Tagalog & 26.7\% & 53.3\% \\
\midrule
\textbf{Overall} & \textbf{33.3\%} & \textbf{53.3\%} \\
\bottomrule
\end{tabular}
\caption{Query translation before embedding, 60-case dev-split preview.
$+20$pp overall, McNemar exact $p=0.0018$ (13 cases flipped
wrong$\to$correct, 1 flipped correct$\to$wrong).}
\end{table}

This has been implemented, not left as an isolated evaluation script:
\texttt{ISCOClassifier} gained an additive, opt-in constructor parameter,
\texttt{translate\_before\_retrieval} (default \texttt{False} --- zero
behavioural change for every existing caller, the same discipline applied
to every other addition in this codebase), with 7 new regression tests
and the full 2,508-test suite green.

\textbf{Honest status, stated plainly rather than overclaimed}: this is a
\emph{dev-split preview}, not a heldout-confirmed result, per this
project's own dev-selects/heldout-confirms discipline (every headline
number in Section~\ref{sec:res-isco} above comes only from the 18,747-case
heldout split). All 14,929 non-English heldout cases have already been
translated and a merged, ready-to-run input file prepared; the final
full-scale retrieval pass is currently blocked by a real, reproducible
memory-exhaustion segmentation fault loading \texttt{multilingual-e5-large}
on the development machine used for this thesis --- the same class of
environment-level constraint already disclosed for the synthetic
ISIC/ISCED-F benchmark's own blocked re-run. The 60-case result is
reported as exactly what it is: a real, statistically significant,
promising preview finding, pending full-scale confirmation.

\subsection{Cross-Standard Coordination and Multi-Step Query Planning: Two
Further Confirmed-Null Results}
\label{sec:results-coordination}

Every classifier evaluated above (Section~\ref{sec:res-isco}) retrieves
independently: ISCO-08, ISIC~Rev.4, and ISCED are each classified from
their own free-text field with no cross-talk between them, and the
Semantic Relation Engine (Section~\ref{sec:arch-sre}) only ever
\emph{scores} the three already-fixed results after the fact --- it never
revises one classifier's output using another's evidence. Two further,
additive, opt-in mechanisms were built and evaluated to test whether real
cross-standard coordination could do better.

\textbf{Mechanism 1 --- deterministic cross-standard coordination.} A
new, pure-Python module reconsiders an already-uncertain ISCO primary
result (fired only when \texttt{hitl\_required} is already \texttt{True})
using the now-known ISIC section and ISCED level: if the primary is
cross-standard-incompatible with both, and one of ISCO's own
already-computed alternatives \emph{is} compatible, the alternative is
promoted. A symmetric forward-direction mechanism lets an already-known
ISCO code bias an ambiguous ISIC guess toward a compatible section. Both
reuse the Semantic Relation Engine's own already-validated compatibility
logic rather than a second hand-built crosswalk table, and both are
wired behind a single opt-in flag, off by default.

\textbf{Mechanism 2 --- multi-step query planning.} A generalisation of
the single-shot corrective-retry pattern already evaluated in
Section~\ref{sec:res-isco}: instead of one LLM-proposed reformulation, an
ambiguous description is decomposed into up to two sub-descriptions, each
re-retrieved independently, and the results reconciled by a disclosed,
provisional highest-score-with-frequency-tiebreak rule. Applied to all
three classifiers (ISCED's version, like its own corrective retry, is
scoped to the FIELD dimension only --- attainment LEVEL stays
deterministic by design).

\textbf{Evaluation data.} Neither mechanism can be tested against WISCO:
directly checking the full 18,747-row heldout export confirmed 0 rows
carry any \texttt{gold\_isic}/\texttt{gold\_isced} value at all --- WISCO
is occupation-only, with no paired industry/education text for the same
respondent. A small, disclosed synthetic combined benchmark ($n=60$,
English, real ISCO-08 codes each paired with an LLM-generated,
definition-grounded (job title, industry, education) triple --- the same
taxonomy-grounded paraphrase methodology already used and disclosed for
the ISIC/ISCED-F benchmark in Section~\ref{sec:res-isic-isced}) was built
to close this specific gap.

\begin{table}[h]
\centering
\begin{tabular}{lrrr}
\toprule
Mechanism & Baseline & With mechanism & McNemar $p$ \\
\midrule
Coordination (legacy profile) & 26.67\% & 26.67\% & $1.000$ \\
Coordination (enriched + e5-large) & 48.33\% & 48.33\% & $1.000$ \\
Query planning (ISCO) & 26.67\% & 28.33\% & $1.000$ \\
\bottomrule
\end{tabular}
\caption{Cross-standard coordination and query planning, $n=60$ synthetic
combined benchmark. Both rows of coordination are byte-identical, 0 of 60

from only 3 discordant cases out of 60 and is not distinguishable from
noise. Query planning changed the ISIC/ISCED prediction in 0 of 60 cases
for both classifiers.}
\end{table}

\textbf{Read plainly: neither mechanism moved accuracy at all.} The
coordination result was deliberately re-run against this project's own
strongest, best-tested retrieval configuration
(enriched catalogue text + \texttt{multilingual-e5-large},
Section~\ref{sec:res-isco}) specifically to rule out the possibility that
a weak baseline was simply leaving no legitimate room for a fix to matter
--- the result held: still byte-identical, still zero cases changed
either way. This extends the project's now-repeated finding that
additional processing sophistication on top of retrieval does not move
ISCO-08 accuracy (Section~\ref{sec:res-isco}'s six independent reranking
and corrective-retry nulls) to a genuinely different mechanism class ---
cross-standard coordination and multi-step decomposition, not just
candidate reranking or single-shot reformulation --- bringing the total
to eight independent confirmed-null results for this general hypothesis
across this thesis's evaluation work.

A real infrastructure bug was found and fixed while re-running the
coordination check on the stronger profile: the evaluation process was
idle long enough for the development machine to sleep, and on waking, the
containerised vector database entered a state Docker's own shallow health
check reported as healthy while its API returned empty replies --- 13 of
60 cases silently received a documented, correct-in-isolation ``no
candidates found'' fallback rather than a real classification, which
looked identical to a genuine negative result in the output file until
inspected directly. Restarting the affected container and re-running only
the corrupted subset (after confirming, not assuming, that available
memory had genuinely recovered from whatever triggered a segmentation
fault on the first retry attempt) produced the corrected, complete result
reported above. This is disclosed here for the same reason every other
environment-level constraint in this thesis is disclosed rather than
smoothed over: a null result is only informative if the pipeline that
produced it is known to have actually run.

\textbf{Honest scope}: $n=60$, English only, synthetic --- a real first
signal for a question no existing dataset in this project could answer,
not a heldout-grade confirmation. A third, more architecturally ambitious
mechanism --- routing classification through a real CrewAI hierarchical
delegation process, with a manager model deciding which classifier to
invoke rather than a fixed call order --- was also implemented (the first
use of CrewAI's hierarchical process anywhere in this codebase) but not
yet evaluated at the time of writing; given the null results above, the
open question it would answer is whether non-deterministic delegation can
find anything the deterministic coordinator's conservative trigger
condition missed, not whether coordination helps in general.

A large, consistent gap: the legacy keyword pipeline is close to

\textbf{A genuine data-quality finding, disclosed rather than hidden}: this
449-row result was computed \emph{before} an automated quality-check tool
(built specifically after this result, to strengthen the evidence further)
found that 2 of the 449 rows (0.45\%) contained a plain LLM safety-filter
refusal stored as if it were valid respondent text --- a real defect in the
generation pipeline, since fixed (the pipeline now detects and retries on
refusal-pattern output), with the two affected rows individually
regenerated and re-verified. The 82.85\%/13.14\% figures above therefore
carry a known, small (0.45\%) contamination not excluded from the
computation --- disclosed exactly rather than silently corrected after the
fact, since re-computing on the corrected, larger dataset (below) was not
completed successfully in this pass.

\textbf{Coverage was subsequently expanded to 1,091 of the full 1,092-row
target (99.9\%)}, with the refusal-pattern defect confirmed fixed at scale
(zero refusal rows across the newly-generated portion) and an independent
automated quality check passing 98.7\% of the full expanded set.
\textbf{A fresh accuracy computation on this larger, fully-corrected dataset
was attempted three times and did not complete}, crashing with a
segmentation fault during embedding-model loading each time under
confirmed low available system memory (as low as $\sim$150MB free on an
8GB development machine, with a permanent, verified fix removing an
unnecessary TensorFlow import applied in between attempts and confirmed to
help, though not enough to fully resolve the crash). \textbf{This is stated
here as a genuine, current infrastructure limitation, not resolved by
further code changes in this pass} --- the 82.85\%/13.14\% figures above
remain this thesis's last successfully computed, citable synthetic
ISIC/ISCED-F result, with its known small contamination disclosed exactly
as described.

\section{Synthetic Pilot-Scale Operational Validation}
\label{sec:res-synthetic-pilot}
% ------------------------------------------------------------

The randomised, ethics-approved pilot described in
Section~\ref{sec:eval-pilot} was not conducted within this project's
timeline --- no application was submitted to the institutional ethics
committee, so no real-respondent data of any kind exists for this thesis.
Rather than leave that gap entirely unaddressed, a deliberately narrower,
explicitly synthetic, single-arm (AI only) operational validation was run
at the same pilot scale ($n=30$). This section reports exactly what that
validation can and cannot support; it is not presented as, and must not be
read as, a substitute for the planned pilot.

\textbf{Method.} Thirty synthetic respondent profiles were constructed by
reusing 30 of 60 already-generated, quality-checked (job title, industry,
education) triples grounded in real ISCO-08 official definitions (the same
taxonomy-grounded LLM paraphrase methodology used for the ISIC/ISCED-F
synthetic benchmark in Section~\ref{sec:res-isic-isced}), combined with
schema-valid canonical answers for the remaining $\sim$35 non-free-text
survey fields. Each profile was driven through the complete, live
conversational system end-to-end via its real HTTP API --- not mocked,
not replayed --- covering the full field-by-field interview, the
validation/confirmation step, and session completion. Classification used
this project's safe, default configuration (21.19\%-class ISCO-08
accuracy; see Section~\ref{sec:res-validity} for why the better-tested
configuration was not used here).

\begin{table}[htbp]
\centering
\caption{Synthetic pilot-scale operational results ($n=30$, 100\% completion, English only).}
\label{tab:ch6-synthetic-pilot}
\small\renewcommand{\arraystretch}{1.4}
\begin{tabular}{lc}
\toprule
\textbf{Metric} & \textbf{Result} \\
\midrule
Sessions completed & 30/30 (100\%) \\

\textbf{What these numbers do and do not mean, stated plainly.}
``Completion time'' here is scripted-driver processing wall-clock time ---
it excludes any human reading, typing, or thinking time, and is therefore
\emph{not} an estimate of a real respondent's completion time, which is
precisely what the planned pilot's own completion-time outcome is designed
to measure. The 100\% clarification-turn rate is likely partly an
artefact of the canonical, machine-phrased answers used to drive the
script (e.g.\ the literal string \texttt{under\_5000}) rather than a
signal about real question difficulty. The 16.7\% live ISCO-08 accuracy
is consistent with, not an independent confirmation of, the already-known
21.19\% default-configuration baseline established on the full 18,747-case
WISCO heldout (Section~\ref{sec:res-isco}) --- at $n=30$ this is within
ordinary sampling variation around that rate, not a new result. The
60\%/73.3\% contradiction rates are real, directly computed signals, but
their magnitude is substantially driven by the live sessions' use of the
lower-accuracy default classifier (so an incorrect ISCO code frequently
and genuinely conflicts with the paired industry/education text) --- they
should not be read as an estimate of how often a \emph{correctly}
classified respondent's answers would be internally inconsistent.

\textbf{On classification accuracy specifically}: a second, offline
measurement of this project's best-tested configuration
(flat retrieval, the enriched catalogue, \texttt{multilingual-e5-large})
against these same 30 cases was attempted, in a process deliberately
isolated from both the live system and the results above. It was not
forced through: the attempt correctly halted under a built-in safety
check after measuring only 463\,MB of genuinely available memory on the
development machine --- the same condition that had caused a reproducible
process crash earlier the same day (Section~\ref{sec:res-validity}). The
existing, full-scale 40.95\% WISCO heldout result
(Section~\ref{sec:res-isco}) is cited in its place, which is the more
statistically defensible number in any case: its 18,747-case sample gives
a materially tighter confidence interval than a fresh $n=30$ draw would.

\textbf{Honest scope.} This validation provides real, synthetic-data,
single-arm operational evidence: the system reliably completes a full
multi-field interview (100\%/30) in bounded processing time, and the
cross-standard contradiction-detection mechanism fires on a real,
computable signal. It provides \emph{no} evidence on respondent
satisfaction, no AI-versus-traditional-interviewer comparison, and no
respondent-realistic completion-time figure --- exactly the primary
outcomes the planned pilot (Section~\ref{sec:eval-pilot}) was designed to
measure, and exactly what remains open, unchanged by this validation.

% ------------------------------------------------------------
\section{Threats to Validity}
\label{sec:res-validity}
% ------------------------------------------------------------

\textbf{No real-respondent evaluation exists for any of the three
classification standards' headline claims beyond WISCO.} ISCO-08's 40.95\%
result is external and real (WISCO), but ISIC/ISCED-F's 82.85\%/13.14\%
result is synthetic, measuring recovery of an LLM's own generating prompt,
not real-respondent accuracy --- this is the single largest validity
limitation in this thesis, stated plainly.

\textbf{ISIC/ISCED-F catalogue coverage.} The live-indexed catalogue covers
134 of 419 official ISIC Rev.~4 classes and 63 of approximately 80 ISCED-F
detailed fields --- stated exactly, not as ``100+ of 238'' as an earlier
internal draft of this thesis stated (which understated the true official
class count for ISIC Rev.~4 as well as overstating coverage).

\textbf{The real, ethics-approved pilot study has not run.} Every claim in
this thesis about respondent burden, cost reduction, or satisfaction
versus a traditional interview is, at most, a target or a plan --- never a
measured result. The synthetic $n=30$ operational validation
(Section~\ref{sec:res-synthetic-pilot}) does not change this: it was
explicitly scoped to measure only what synthetic data can honestly
support, and respondent satisfaction and the traditional-interviewer
comparison are not among those things.

\textbf{Single-machine measurement, and a real, caught production-stability
finding.} All computational-efficiency figures
(Section~\ref{sec:res-efficiency}) are from one local development machine,
not a production environment, and that machine's own memory constraints
directly blocked a planned re-computation of the ISIC/ISCED-F synthetic
result at full dataset coverage (Section~\ref{sec:res-isic-isced}) ---
disclosed as a real limitation of this thesis's own evaluation
infrastructure, not glossed over. The same constraint was found to be more
serious than a slow evaluation re-run: switching the live survey system's
classifiers to the best-tested configuration (flat retrieval, the
enriched catalogue, \texttt{multilingual-e5-large}) reproduced a genuine
process crash on this machine under real memory pressure --- a catchable
error in some attempts, an uncatchable segmentation fault that terminated
the entire server process in others. This was caught by live-testing the
change against the running system before accepting it, not assumed safe
because unit tests passed, and was reverted the same day: the live system
runs its earlier, lower-accuracy default configuration, while the
better-tested configuration remains valid and is used only in isolated,
memory-checked offline evaluation runs (exactly how every headline
accuracy figure in this chapter was actually produced).
