\chapter{Implementation}
\label{chap:implementation}

The prototype combines a Next.js interface, a FastAPI backend, PostgreSQL
records, Qdrant retrieval, Redis context storage, and configurable language
models. This chapter describes its components and current limitations.
Evaluation configurations are distinguished from interactive defaults.

\section{Deployment Configuration}
\label{sec:impl-docker}

The repository provides a Windows script and Docker Compose configuration:
\begin{lstlisting}
start.bat
docker compose -f docker/docker-compose.yml up --build
\end{lstlisting}

The Windows script installs dependencies, runs \texttt{alembic upgrade
head}, and starts the native application with containerised infrastructure.
Compose defines PostgreSQL, Redis, Qdrant, backend, and frontend services.
Ollama is configured separately through its server URL.

A first-boot defect remains in the backend Dockerfile. Its initialization
command imports the declarative \texttt{Base} and invokes
\texttt{create\_all()} without first importing model declarations.
The metadata is empty at that point, so a fresh PostgreSQL volume does not
receive the tables. A previously initialized database can conceal the
problem. The image also omits the root Alembic configuration. The Compose
command cannot yet be treated as a validated fresh installation procedure.

The \texttt{/ready} endpoint checks database connectivity with
\texttt{SELECT 1}, not schema presence, classifier availability, or
end-to-end survey readiness. Qdrant collection counts and installed model
counts depend on the profiles built and models downloaded; they are not
architectural constants.

Migrations introduce the initial schema, HITL tables, soft-delete
timestamps, response revision links, and report enrichment columns. ISIC,
ISCED, and semantic-coherence JSON are stored alongside report text,
enabling those fields to survive cache reads.

The response model provides \texttt{supersedes\_id} and
\texttt{deleted\_at} for revision history, but not all write paths use
them. Duties-based occupation refinement can be returned to the interface
without replacing the stored classification. A corrected job title can
remain only in context when entity extraction does not create a new
response; completion skips an already-stored job title, leaving the report
with the earlier answer. These persistence limitations remain unresolved.

Deleting a session sets a timestamp and retains its records. The prefill
query does not currently exclude deleted sessions or inactive response
revisions, so deleted answers can enter a new interview. Soft deletion
implements retention and visibility checks in selected routes, not
verified erasure.

\section{Classification Catalogues and Embeddings}
\label{sec:impl-kb}

Official ISCO-08 catalogue profiles contain 436 unit
groups~\cite{ilo2012isco_v1}. Their loader verifies counts
and source hashes. Enriched profiles add definitions, tasks, and example
occupations from the source workbook to title-only embedding text. Small
and large multilingual E5 encoders use separate profiles; results are
presented in Chapter~\ref{chap:results}.

The live survey route initializes \texttt{ISCOClassifier()} without an
explicit profile. The constructor defaults to the legacy catalogue,
hierarchical retrieval, and the small embedding model. This differs from
the official, enriched, large-encoder flat configuration used for the best
full-heldout retrieval result. Neither official-profile coverage nor that result
should be attributed to the live default.

Retrieval may be followed by LLM reranking when an agent is available and
the score is below 0.92. The unpinned constructor uses
\texttt{TaskType.GENERAL}; an explicitly specified reranker uses the strict
model factory. Failure to initialize the unpinned agent permits
retrieval-only classification. The threshold is a configured rule, not
evidence of a calibrated probability of correctness.

ISIC and ISCED classifiers expose legacy and retrieval-based methods.
Education level and field-of-study code are separate outputs. Each
experiment and the interactive route must be identified by their selected
methods, rather than assumed to use every available retrieval option.

\section{Language Processing}
\label{sec:impl-lang}

Five languages are exposed: English, Arabic, Urdu, Hindi, and Tagalog,
with separate \texttt{ar} and \texttt{ar-gulf} codes for Arabic variants.
An \texttt{other} code handles uncertain or unsupported input. Detection
combines \texttt{langdetect.detect\_langs()} with script heuristics,
including a Devanagari fast path for Hindi and Gulf lexical markers.
A GENERAL model agent extracts named entities; failure can produce an
empty entity list.

Code-switch detection identifies Arabic--Latin or Devanagari--Latin input
when both script proportions meet the 0.10 threshold. It cannot establish
every language switch, particularly between languages sharing a script.
Normalisation is similarly limited to the dictionary entries.

Translated prompts and options are implemented, but complete multilingual
routing has not been established. Hindi and Urdu employment-status buttons
send translated labels that the status extractor does not normalize
reliably. Clarification fallback can store an invalid status and truncate
the subsequent field order. The operational validation is English only.
Interface availability must therefore be distinguished from validated
interview routing, comprehension, and completion.

\section{Validation and Quality Review}
\label{sec:impl-validation}

The \texttt{ValidationAgent} checks ten deterministic rule identifiers:
\begin{itemize}
  \item R01 requires employment status and industry; employed respondents
  additionally require job title, weekly hours, and employment type.
  \item R02 requires supplied hours to be numeric.
  \item R03 checks weekly hours in $[1,168]$; R04 warns above 80.
  \item R05 and R06 flag an unemployed respondent's current job title or
  positive weekly hours.
  \item R07 flags a current job title outside the labour force.
  \item R08 warns about full-time work below 20 hours; R09 warns about
  part-time work at 35 hours or above.
  \item R10 flags zero hours for an employed respondent.
\end{itemize}

These are selected consistency checks, not a complete implementation of
international labour-force classification requirements. R01 requires
industry for every status, although inactive questionnaire paths do not
collect current industry; those requirements need reconciliation.

When deterministic checks contain no errors, \texttt{validate()} attempts
a CRITICAL semantic-model check. The live route calls this method at the
validation state without explicitly disabling that stage. Initialization
or runtime failures may be caught by the route. A validation result is
therefore not guaranteed on every turn, and validation is not a mandatory
completion gate.

The Semantic Relation Engine applies hand-built occupation--industry and
occupation--education plausibility rules. It consumes an ISCED~2011 level,
not an ISCED-F detailed field. HIGH violations can create review entries
during a turn; report generation adds a backstop for later detection.
This is an implemented escalation path under tested conditions, not
empirical validation of the crosswalk. Appendix~\ref{app:sre-demo}
describes its rule-consistency evidence.

\section{Frontend}
\label{sec:impl-frontend}

Four pages provide OTP login, conversation, bilingual report display, and
supervisor review. Chat renders the next field, progress, classifications,
and a structured correction picker. Reports display occupation, industry,
education, and coherence summaries.

The skipped-question display uses a fixed 155-question comparator without
a verified mapping to the implemented field order. The \emph{AI Verified}
badge depends only on occupation confidence and can overlook semantic
escalation. The supervisor table reads a confidence property differing
from \texttt{ai\_confidence} in the API. These displays are not evidence of
measured efficiency or completed review.

\section{Security and Data Governance}
\label{sec:impl-governance}

JWT authentication and ownership checks protect ordinary session routes.
Email-code request limits and shared OTP attempt counters use Redis, with
an in-process fallback. CORS uses a configured origin allowlist, and
middleware adds response security headers.

HITL endpoints do not enforce a supervisor role or authority over the
target respondent. An ordinary account can list the global queue and
change another respondent's classification. SMS-code requests lack request
limits. These gaps prevent a claim of readiness to collect participants'
personal data.

Email and phone identifiers remain linked to survey records. The person
register is a prefill store, not a pseudonymisation mechanism. Logging and
retention-purge helpers do not establish comprehensive access logging,
scheduled purging, or regulatory compliance. GENERAL routing can use
configured cloud providers when the local model is unavailable, so local
inference is not a guaranteed boundary for respondent text. The proposed
study needs an approved data-management plan addressing these issues
(Appendix~\ref{app:consent}).

\section{Testing and Scope of Verification}
\label{sec:impl-testing}

Tests under \texttt{backend/tests/} and \texttt{eval/} exercise rules,
routing, retrieval contracts, persistence, and evaluation calculations.
Many substitute model or service responses. Passing tests establish
checked software properties, not multilingual accuracy, regulatory
compliance, or complete service reliability.

The documented 16 September 2026 run recorded 2,567 passing tests and one
slow test deselected. Historical runs with several
\texttt{PYTHONHASHSEED} values demonstrate repeatability under tested
conditions, not absence of every defect or nondeterministic behavior.
A focused review on 3 October 2026 passed 194 existing conversation,
orchestration, and evaluation tests while identifying unresolved defects.
A fresh deployment, full current suite, browser assessment, and
participant study were outside that review.

The legacy BM25 comparison uses developer-authored synthetic cases.
The principal occupation benchmark and its limitations are described in
Chapter~\ref{chap:evaluation}.
