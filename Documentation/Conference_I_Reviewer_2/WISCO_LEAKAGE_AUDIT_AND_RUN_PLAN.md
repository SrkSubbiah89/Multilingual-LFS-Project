# WISCO Benchmark Leakage Audit and Execution Plan

Conference I Reviewer #2 response, Step 7A: "perform a strict WISCO
benchmark leakage audit, validate the group-aware split, and prepare a
cost/time-aware execution plan." **No classifier, LLM, Qdrant, or network

## Phase A — Why 4,232 source records became 20,760 prepared records

`backend/evaluation/wisco/data/processed/wisco_raw_parsed.json` has 4,232
occupation records, each with a `titles` dict holding up to 5 language
variants (`en`/`ar`/`ur`/`hi`/`tl` — this project's target languages, a
subset of WISCO's 61 base languages). `eval/build_wisco_isco_benchmark.py`
emits **one `BenchmarkRecord` per (occupation, language) pair that actually
has a title in that language** — i.e. the expansion is **language
variants**, not translations generated by this project, not aliases, not
duplicate titles, not augmented text, and not multiple classifications of
one text. Confirmed exactly: per-language non-empty title counts (en 4,230
/ ar 4,167 / ur 3,989 / hi 4,202 / tl 4,172, from
`Documentation/Phase_2/Week_1/PROVENANCE.md`) sum to exactly **20,760** —
matching the prepared record count precisely, with no unexplained residual.
Missing (occupation, language) combinations (e.g. 4,232 − 3,989 = 243
occupations with no Urdu title) are **skipped, never fabricated** — see
`build_wisco_isco_benchmark.py::build_records()`'s `if not text: continue`.

### B.1 Source-family split check — **LEAKAGE-FREE**

0 of 4,232 source keys appear in both `dev` and `heldout`. v1's per-key

### B.2 Text-duplicate check — **4 CROSS-SPLIT DUPLICATE GROUPS FOUND**

9 exact-duplicate-text groups exist *within* a single split (harmless for
leakage purposes). **4 groups span dev and heldout** — in every case, two
*different* WISCO occupation keys share byte-identical normalized title
text in one language, and (checked individually) an identical gold ISCO-08
code:

| Language | Dev key | Heldout key | Shared text | Gold code (both) |
|---|---|---|---|---|
| hi | 2643001800016 | 2643000400018 | "शपथबद्ध अनुवादक" | 2643 |
| tl | 2643001800016 | 2643000400018 | "Nanumpang tagasalin" | 2643 |
| ar | 3434010200000 | 3434010000000 | "طاهي" | 3434 |
| ar | 4221001900018 | 4221001500018 | "موظف حجوزات سفر" | 4221 |

This is a genuine WISCO source-data phenomenon (its own occupation
dictionary contains near-synonym duplicate entries under the same unit
group), not a bug in this project's parsing or splitting. It is real
leakage under a strict definition: a system could see one occupation's
exact title during dev-based parameter selection and be evaluated on the
literal same text (different record ID, same code) in heldout.

## Phase C — Split correction

**Leakage was found (Phase B.2)** — per the task's Phase C.2 branch, a new
versioned benchmark directory was created:
**`eval/local_benchmarks/wisco_isco08_v2_group_split/`**. v1 was **not
altered, deleted, or regenerated** — it remains on disk exactly as Step 6
produced it, now serving as the audit record of this finding.

**Grouping method**: union-find over the 4,232 WISCO occupation keys.
Two keys are merged into one family whenever they share byte-identical
normalized title text in *any* target language (not just the 4 pairs found
leaking in v1 — 12 merge events were found in total when checked
exhaustively, since some duplicate-text pairs happened to already land in
the same split under v1's per-key hash and so weren't flagged as
"cross-split" by the v1 audit, but are still the same underlying leakage
risk under a re-split). Each resulting family (4,220 families from 4,232
keys) is assigned exactly one split via a **fixed seed (42)**, sha256-hashed
over the family's sorted member keys — see
`eval/build_wisco_isco_benchmark_v2_group_split.py`'s module docstring for
the exact, reproducible algorithm.

**Result**: 20,760 records, **2,013 dev / 18,747 heldout** (v1 was 2,005 /
18,755 — a shift of 8/8 records from the 12 merged families landing on
whichever split their family hash selected). Re-running the full leakage
audit against v2:

```
leakage_found=False
overall_ok_no_leakage=True
n_leaking_source_keys=0
n_exact_duplicate_groups_cross_split=0
integrity ok=True, hash_match=True
```

each Tier-1/Tier-2 config invocation as atomic (rerun from scratch on
failure) given the ≤2.6-hour-per-config scale established above, rather
than relying on partial-output recovery that the current tooling does not

## Post-execution update: Task 12 (Tier 1 run) and Task 13 (integrity fix)

Everything above this section was written **before** Tier 1 was actually
run and describes the plan, not the outcome. This section records what
actually happened and must be read alongside it.

### Task 12 — the first full Tier-1 run was halted, not completed

Task 12 executed both full Tier-1 configurations (18,747 cases each,
`--use-llm-reranker off`, flat then hierarchical) exactly as planned
above. Both commands exited 0 and wrote complete 18,747-row CSVs, but the
**hierarchical** output failed the mandatory output-integrity gate: 23 of
18,747 rows (0.123%) carried a `flat_semantic` method label instead of
genuine hierarchical retrieval — a real integrity problem, not merely a
stray edge case, per this project's evidence-safety discipline. Per that
gate's own explicit rule, Task 12 stopped before any accuracy analysis or
manifest was produced — **no measured Tier-1 metric exists from that
run**. Two of the 23 fallback rows, plus a third row that did not fall
back, showed severe anomalous single-stage latency (up to ~4 hours for
one case), together accounting for ~85% of the hierarchical run's 5h21m
wall time; the flat run showed no such anomaly anywhere. Full detail:
`Documentation/AI_HANDOFF/CLAUDE_TASK_12_FINAL_REPORT.md`.

### Task 13 — root-cause fix for the 21 fast fallbacks, and new safeguards

Direct code inspection (not merely inference from the CSV) confirmed a
reproducible cause for the 21 fast (non-anomalous-latency) fallbacks:
`ISCOClassifier` supplies a keyword-derived `major_hint` by default;
`HierarchicalISCOStore._hierarchical_search()` anchors the entire search
to that one hint as a single-branch `SeedSpec`, skipping semantic stage 1
entirely; if that one anchored branch reaches no stage-4 result, the
generic engine returns `None` and the store silently fell straight
through to flat search. Task 13 fixed this: the store now retries the
same generic engine exactly once, unseeded (normal semantic stage-1
retrieval), before falling back to flat — see
`backend/rag/hierarchical_store.py`'s "Retrieval outcomes" docstring
section for the resulting four-state model (successful keyword-anchor
route / recovered semantic-stage route after a failed anchor / explicit
flat fallback / total unavailability). A failed seeded attempt's trace
data is never merged with a successful retry's — only the winning
attempt's genuine stage 1-4 evidence is ever recorded.

Task 13 does **not** claim to have found or fixed the 2-3 severe-latency
stall cases' root cause — that remains unconfirmed. It adds a bounded,
configurable Qdrant request timeout (default 30s,
`QDRANT_TIMEOUT_SECONDS` override) so a future stall raises a catchable
exception instead of blocking indefinitely, making it diagnosable rather
than silent — this bounds a *class* of indefinitely-blocked requests, it
does not prove or fix what caused the Task 12 stalls specifically.

Task 13 also added `eval/run_eval.py --require-genuine-hierarchical`
(optional, valid only with `--system hierarchical`) plus an opt-in
`--max-stage-latency-ms` threshold: together they make any future Tier-1
attempt fail fast and non-zero, writing no result CSV at all, the instant
any case falls back, is missing stage evidence, or exceeds a configured
per-stage latency bound — so a contaminated run can never again produce
output that looks like complete, valid benchmark evidence. Full detail:
`Documentation/AI_HANDOFF/CLAUDE_TASK_13_FINAL_REPORT.md`.

**Still not run to completion with valid results.** Task 13 is a targeted
